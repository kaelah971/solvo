# M11.6 — Per-Recipient Claim-Link Batches: Design

Date: 2026-08-13
Branch: `feature/smarter-claim-links`
Status: **DESIGN ONLY. No production behavior implemented in this step.
Batch implementation is explicitly DEFERRED out of M11** (milestone
decision): batch-signal claim phrases (`claim links` plural or `N claim
links`) decline with "Claim-link batches are not supported yet. Create one
claim link at a time." and zero artifacts until a later roadmap slice.

## Summary

M7–M11.5 shipped single claim links (one-time 192-bit tokens, hash-only
persistence, recipient wallet entry that never moves funds, human approval
gate, computed expiry, reissue = new claim) plus the M11.2 read model, M11.3
Telegram status UX, M11.4 web status UX, and M11.5 expiry/reissue rules.
M10 shipped natural-language BATCH PAYOUTS for fully-resolved recipients
(G1/G2/G3, all-or-clarify, one `pending_approval` payout + N items).

M11.6 designs the third surface: **creating N claim links from one
instruction** — for recipients whose wallets are NOT known yet. It is a
**batch of claim LINKS**, not a batch of payouts: nothing is resolved to a
wallet, nothing is approved, nothing executes. Like single claims, each link
collects its own destination from its own web page later, and each requires a
human approval of the exact claimed destination before KeeperHub execution.

This document is design only. Implementation is sliced into M11.7–M11.12
(§11) with a locked corpus baseline first, mirroring the M10.2 baseline
discipline: current behavior ("batch claim phrases → clarification/
unsupported, zero artifacts") is frozen by tests BEFORE any parsing lands.

## 1. Supported v1 grammar

The smallest safe set: **uniform amounts, explicit counts or labels only**.

| Form | Example | Semantics |
|---|---|---|
| G1 — count-based uniform | `create 3 claim links of 0.01 USDC each`<br>`make 2 claim links for 0.05 USDC each` | Exactly N claim links, same amount, same expiry; no labels (or "link 1…N" labels) |
| G2 — named uniform | `create claim links for blossom and endurance, 0.01 USDC each`<br>`make claim links for daniel and the winner, 0.05 USDC each` | One claim link PER NAME; names are **labels only**, never resolved wallets; same amount per link |

Grammar rules:

- A **batch signal is mandatory**: `claim links` (plural) + `each`, or an
  explicit count (`<integer> claim links`). Without the signal, existing
  single-claim rules apply unchanged (`create a claim link for 0.05 USDC`).
- **Count must be an integer 1–10.** `3 claim links` or `2 claim links`.
  Counts above 10 are blocked (reply says the cap), never truncated.
- **Amounts are uniform in v1**: `each`/`of … each` forms only. Amount is
  positive decimal USDC, ≤ 6 decimals, Base USDC only (workspace chain/token).
- **Named labels (G2) are labels only.** `blossom` never resolves to the
  workspace recipient directory; the claim link's destination is always
  entered by the recipient on the web page. If a label happens to match a
  registered alias, it is still just a label — the reply copy says
  "Recipients enter their own wallet via the link." (No wallet pre-fill, no
  `/pay` routing, no mixed semantics.)
- G2 names are separated by `and`, commas, or `&`. Duplicate labels in one
  request clarify (no silent dedupe).
- Labels may be plain words/names (registry aliases, names, "the winner").
  Collective/group words WITHOUT a count stay invalid (M9 lock: `everyone`,
  `contributors`, `the team` are never recipients).
- Trailing reason copy after the amount is ignored for v1 (claims have no
  memo field; mirrors single-claim behavior).

### Explicitly designed but DEFERRED in v1

- **G3 — count-only generic nouns:** `make claim links for three winners,
  0.01 USDC each` → 3 links labeled "winner 1..3". The `N <noun>` form is
  unambiguous ONLY for a small allowlist of generic nouns (winners,
  recipients) and needs label-generation + collective-word care; deferred to
  avoid any overlap with the M9 "never recipients" lock.
- **G4 — per-claim different amounts:** `0.01 USDC for winner one, 0.02 USDC
  for winner two`. Deferred: per-link amount accounting, per-link policy
  checks, and a richer parser surface are not worth v1 risk.

## 2. Explicitly deferred

| Feature | Reason |
|---|---|
| CSV import / bulk upload | `/batch` command family; no NL CSV parsing |
| Public claim pools / marketplace links | Public discovery is a separate product surface |
| `pay everyone` / `pay all contributors` / `pay the team` | No explicit count or names; M9 lock: group words never become artifacts |
| Unresolved M10 mixed payout+claim batch | Requires a mixed-decision shape and complicates approval semantics (M10 §7 explicitly defers) |
| `turn unresolved batch recipients into claim links` | Same mixed-batch reason; defer until M10.9+ slice |
| G3 count-only generic nouns (`three winners`) | Designed, deferred (see §1) |
| G4 per-claim different amounts | Designed, deferred (see §1) |
| Claim links with auto-approval / direct execution | Authority boundary; always human approval |
| Judge Mode claim batches | Judge remains `/judgepay`-command only; NL never reaches Judge |
| Private/DM batches | NL agent remains community-chat only |
| Changing destination after claim | Immutable `claimed_recipient` (M7 contract) |
| Raw token re-display | One-time links; shown once at creation only |
| Reissue of a batch (all links at once) | Per-link reissue via M11.5 rules; batch reissue is a later slice |
| Claim-link batch status summary command | Designed in §7; implemented after batch creation ships |

## 3. Authority boundary

Batch claim links MAY ONLY create N `claim_links` rows and return N one-time
raw URLs. They must never:

- approve or self-approve any link or the batch;
- execute, simulate, retry, or submit anything;
- call KeeperHub;
- create `payouts`/`payout_items` rows at creation time (a payout exists only
  after a human approves a claimed destination, via the existing claim
  approval pipeline — one payout per link);
- bypass the owner/approver (separation of duty: the requester cannot approve
  their own claim);
- resolve named labels to wallets;
- expose token hashes (only the raw token once + prefix where existing copy
  already shows it);
- re-show raw tokens after the initial reply;
- use Judge Mode.

Enforcement mirrors M8/M10: deterministic extraction → schema-validated
interpretation → planner (all-or-clarify) → application-owned bridge → N
claim rows + audit. The bridge never imports execution/KeeperHub modules
(source-contract tests apply).

## 4. Persistence / state approach

**N independent `claim_links` rows. No schema change, no migration.**

- One `claim_links` row per link, exactly like `createClaimLink` today:
  new id, new token_hash/token_prefix, `status = 'created'`, per-link
  `expires_at`, same `amount_base_units`/`currency_symbol`/`chain_id`/
  `token_address`/`workspace_id`/`requester_id` for the uniform batch.
- **Batch linkage without a table:** a deterministic batch id derived from
  the instruction, e.g. `batch:<run.idempotency_key>:claimbatch` (agent flow)
  or `tg:<chat>:m<messageId>:claimbatch` (future slash command), recorded in
  each link's audit metadata (`event_type = 'claim_created'`, metadata
  `batchId`, `batchIndex`, `batchSize`, `amountBaseUnits`, `expiresAt`,
  `tokenPrefix`) and on the agent-run decision record. No batch table, no
  shared state machine.
- **Per-link idempotency keys:** `ag:<run.idempotency_key>:claim:<index>`
  (index 0..N-1), mirroring the single-claim key shape
  (`…:claim`) and the M10 batch key family (`…:batch:<n>`). Creation is
  serialized inside one transaction (advisory lock on the first key);
  concurrent/duplicate deliveries resolve to ONE batch.
- **Statuses are per-link and independent**: each link runs the existing
  lifecycle (`created → claimed → approved → executed | cancelled`,
  computed `expired`). A batch is never a state machine of its own.
- **Raw tokens are returned once** in the initial reply only; only hashes and
  8-char prefixes are persisted; secure links are never recoverable later.

## 5. Telegram UX

Fresh reply (builders in `claim/messages.ts`; banned internal terms apply):

```
CLAIM LINK BATCH CREATED
Links: 3
Amount each: 0.01 USDC
Expires: 2026-08-20 13:00:00 UTC
1. https://solvo.example/claim/<token-a>
2. https://solvo.example/claim/<token-b>
3. https://solvo.example/claim/<token-c>

No funds move from these links.
Recipients enter their own wallet via the link.
An owner or approver must approve each exact claimed destination before KeeperHub execution.
Secure links cannot be shown again.
```

**Link list decision:** show ALL raw links in the fresh reply, one per line,
because the links must reach the recipients and cannot be recovered later.
This drives the cap: **max 10 links** keeps the reply well under Telegram's
4096-char limit (~35 chars per link × 10 + header). Named batches (G2) prefix
each line with the label: `1. blossom — <url>`; count batches use
`1. link 1 — <url>` or bare lines.

Truthfulness contract: "No funds move from these links." / approval gate
copy / "Secure links cannot be shown again." Never says paid/sent/completed/
executed; no hashes; no internal terms; no `agent_run`/provider/planner
language.

## 6. Duplicate / no-token-reveal behavior

Re-delivery of the same instruction short-circuits at the agent-run
idempotency layer (existing M8 semantics) and replies:

```
CLAIM LINK BATCH ALREADY CREATED
Links: 3
Amount each: 0.01 USDC
Expires: 2026-08-20 13:00:00 UTC
State: 3 pending

No duplicate claim links were created.
The secure one-time links cannot be shown again.
```

- No raw tokens in duplicate replies — ever.
- Shows count, amount, expiry, and a per-link status summary (see §7) only.
- No duplicate claim rows, no duplicate `claim_created` audits.

## 7. Claim status summary

Per-claim status counts via the existing M11.2 read model
(`getClaimStatusForMember` per link, effective statuses). A future
`/claimbatchstatus <batch-id>` (or NL `check claim batch <id>`) would print:

```
CLAIM BATCH STATUS
BATCH        <batch-id>
LINKS        3
PENDING      2
CLAIMED      1
APPROVED     0
COMPLETED    0
EXPIRED      0
REJECTED     0
```

- No raw tokens, no token hashes, no full claim ids in the public reply
  (claim ids stay in the fresh/duplicate replies' scope for the requester).
- Same-workspace active-member gate and generic no-leak reply as M11.3.
- Implemented after batch creation ships; the count aggregation is a pure
  function over the N link views.

## 8. Interaction with M10

- **M10 explicit batch payouts are for KNOWN recipients** (resolved aliases /
  0x addresses → one `pending_approval` payout + N items).
- **M11 batch claim links are for UNKNOWN recipients** (no wallet known yet →
  N `claim_links` rows; wallets come from each link's web page).
- **No mixed known-payout + unknown-claim batch in v1.** A message that mixes
  resolved-payment language with claim-link language → clarification, zero
  artifacts. Examples: `pay blossom 0.01 USDC and create a claim link for
  endurance` → clarify; `pay blossom and endurance 0.01 USDC each` stays an
  M10 batch payout (never becomes claim links just because a name is missing).
- `turn unresolved batch recipients into claim links` stays deferred (M10 §7):
  it requires a mixed-decision shape.
- Grammars are mutually exclusive by verb family: `pay/send/split … each`
  = M10 payout batch; `claim links … each` = M11 claim-link batch.

## 9. Limits / policy

| Limit | Value | Notes |
|---|---|---|
| Max links per batch | **10** | Telegram reply length + conversational parsing sanity; count must be integer 1–10 |
| Min links | 1 | A count of 1 is a valid (uniform) batch; single-claim wording still routes to single-claim |
| Amount per link | Workspace per-transaction limit | Same `evaluateCommunityRequest` policy as single claims |
| Batch total | per-link × N vs workspace daily limit | Checked at creation (defense-in-depth recheck; the per-claim approval-time check remains authoritative) |
| Expiry | default 168h, configurable via `CLAIM_EXPIRY_HOURS` | Per-link, computed, never stored as `expired` |
| Currency/chain | Base USDC only | Workspace `chain_id`/`token_address`; anything else fails closed |
| Amounts | positive decimal, ≤ 6 decimals | Existing amount grammar; zero/negative/exponent forms rejected |
| Duplicate labels | whole batch clarifies | No silent dedupe |
| Rate limits | M8 per-user hourly/daily run caps apply unchanged | — |
| Batch id | deterministic from the instruction | `batch:<run.idempotency_key>:claimbatch` |

Groups: corpus baseline, parser/interpreter, planner, bridge/persistence,
Telegram routing, duplicate/no-token-reveal, status summary, web claim

concrete phrases/actions:

**G1 count-based uniform → batch claim created (N rows):**
1. `create 3 claim links of 0.01 USDC each` → 3 claim rows, 3 links returned
2. `make 2 claim links for 0.05 USDC each` → 2 claim rows
3. `create 10 claim links of 0.001 USDC each` → 10 rows (cap boundary)
4. `create 1 claim link of 0.01 USDC each` → 1 row (uniform batch, not single wording)
5. `please create 5 claim links of 0.01 USDC each` → 5 rows
6. `create 3 claim links of 0.01 usdc each` (lowercase) → 3 rows

**G2 named uniform → batch claim created with labels:**
7. `create claim links for blossom and endurance, 0.01 USDC each` → 2 rows, labels blossom/endurance
8. `make claim links for daniel, the winner, 0.05 USDC each` → 3 rows
9. `create claim links for blossom and endurance 0.01 USDC each` (no comma) → 2 rows
10. `create claim links for blossom & endurance, 0.01 USDC each` → 2 rows

**Clarification / blocked (zero artifacts):**
11. `create claim links of 0.01 USDC` (no count, no names) → clarification (amount only)
12. `create 0 claim links of 0.01 USDC each` → blocked (count must be 1–10)
13. `create 11 claim links of 0.01 USDC each` → blocked (cap 10)
14. `create claim links for blossom and blossom, 0.01 USDC each` → clarification (duplicate label)
15. `create claim links for blossom, 0.01 USDC each` (single label, no batch signal) → single-claim path unchanged
16. `create 3 claim links of 0.01 ETH each` → unsupported (token)
17. `create 3 claim links of 0.01 USDC each on Celo` → unsupported (chain)
18. `create 3 claim links of 0 USDC each` → invalid amount
19. `create claim links for everyone, 0.01 USDC each` → clarification (group word, no count)
20. `create 3 claim links` (no amount) → clarification (missing amount)
21. `make claim links for three winners, 0.01 USDC each` → unsupported in v1 (G3 deferred)
22. `create claim links: 0.01 USDC for winner one, 0.02 USDC for winner two` → unsupported in v1 (G4 deferred)

**M10 interaction:**
23. `pay blossom and endurance 0.01 USDC each` → M10 prepared batch payout (unchanged)
24. `pay blossom 0.01 USDC and create a claim link for endurance` → clarification (mixed, no artifact)
25. `split 0.02 USDC between blossom and endurance` → M10 prepared batch (unchanged)
26. `turn unresolved batch recipients into claim links` → clarification (deferred)

**Persistence / state:**
27. batch creation writes N `claim_links` rows, no `payouts`/`payout_items`/execution attempts
28. per-link idempotency keys `ag:<run.key>:claim:<n>` are unique and stable
29. batch id recorded in audit metadata (`claim_created` × N with batchId/batchIndex/batchSize)
30. each link has independent `expires_at`, `status = 'created'`, hash-only token persistence
31. duplicate delivery → `CLAIM LINK BATCH ALREADY CREATED`, N rows total (no duplicates), no tokens re-shown
32. concurrent duplicate deliveries → exactly N rows

**Status summary:**
33. per-link counts aggregate pending/claimed/approved/completed/expired/rejected correctly
34. batch status reply contains no raw tokens, no hashes, no full claim ids
35. batch status follows the same-workspace/no-leak gate (generic reply for outsiders)

**Web claim compatibility:**
36. each created link resolves on `/claim/[token]` to the valid state with the shared amount/expiry
37. claiming one link never affects the other links' states
38. web submit on any batch link follows M7 rules (record only, no payout, no execution)

**Expiry / reissue interaction:**
39. an expired link in a batch reads `expired` while sibling links stay `pending`
40. a link from a batch can be reissued via M11.5 `reissueClaimLink` as an individual link
41. reissue of a batch link never resurrects the old link and never touches siblings

**Adversarial / truthfulness:**
42. `create 3 claim links of 0.01 USDC each and approve them` → unsupported, zero artifacts
43. `create 3 claim links of 0.01 USDC each and execute now` → unsupported, zero artifacts
44. `create 3 claim links of 0.01 USDC each fake proof` → unsupported, zero artifacts
45. `create 3 claim links of 0.01 USDC each bypass limits` → unsupported, zero artifacts
46. fresh batch reply contains no hashes, no agent-run/provider/planner terms, no raw JSON, no "paid/completed"
47. forged agent_run with fake hashes cannot change batch creation or status replies
48. batch bridge imports no KeeperHub/MCP/execution/judge/webhook/model modules
49. raw tokens from a batch are redacted by `redactSecrets` in logs
50. Judge-like batch phrasing never reaches Judge Mode

## 11. Implementation plan (tasks)

**Deferral note:** the M11 milestone ships claim status, Telegram status,
web status, expiry/reissue, and the adversarial/truthfulness gate; batch
claim-link IMPLEMENTATION is deferred to a later roadmap milestone. The
slice plan below is the reference for that future work (batch-signal phrases
currently decline with zero artifacts, locked by
`tests/security/claim-link-truthfulness.test.ts`).

- **Slice 1 — batch claim-link grammar/corpus baseline (tests only):** add
  the phrases from §10 to a batch-claim fixture with CURRENT expectations
  (clarification/unsupported, zero artifacts); lock "no batch yet" by tests
  (mirrors M10.2). No parser changes.
- **Slice 2 — batch parser/planner:** deterministic count/label parsing
  (G1/G2), uniform amount computation, label list splitting, duplicate-label
  rejection, `AgentIntentKind`/interpretation extension, planner decision
  (`prepared_claim_link_batch`) with all-or-clarify + policy checks
  (`evaluateCommunityRequest` per link + total check). No persistence yet —
  planner returns `unsupported` until the bridge slice.
- **Slice 3 — batch bridge/persistence:** `bridgePreparedClaimLinkBatch`
  reusing the single-claim transaction shape N times: serialized creation
  (advisory lock on `…:claim:0`), per-link idempotency keys
  (`ag:<run.key>:claim:<n>`), N `claim_links` rows, batch id in audit
  metadata, N raw tokens returned once. No schema change; no payout/execution.
- **Slice 4 — Telegram reply/copy + duplicate behavior:** batch reply
  builders (fresh + already-created, §5/§6), routing wiring with the existing
  precedence (slash commands and single-claim NL keep priority; batch fires
  only on batch signals), status summary aggregation (§7).
- **Slice 5 — batch adversarial/truthfulness gate:** hostile batch claim
  mutations, forged-run immunity, source contracts, no-token-reveal on
  duplicates, corpus expectation flips (in the same commit as slices 3–4),
  full suite gate.
- **Slice 6 — docs/roadmap final gate:** README roadmap, M9/M10 doc
  cross-references, full gate (`npm test`, `test:db`, lint, tsc, build,
  read-only doctors).

Each task ends with lint + `tsc --noEmit` + the task's test files green.

## Risk register

| Risk | Mitigation |
|---|---|
| Batch reply leaks tokens on duplicates | Duplicate replies show count/amount/expiry/status only; never tokens (locked by tests) |
| Ambiguous "and" misparsed as a batch | Batch only on explicit signals (`claim links` plural + `each`/count); else existing rules |
| Labels misread as resolved recipients | G2 labels never resolve to wallets; copy states recipients enter their own wallet; no `/pay` routing |
| Collective words ("everyone") slip in | Group words without a count stay invalid (M9 lock extended to batch claims) |
| Silent partial batch (some links fail) | All-or-clarify: any invalid label/amount/count blocks the whole batch, zero rows |
| Duplicate label creates two links | Whole-batch clarification, never dedupe |
| Total over daily limit at creation | Total = per-link × N checked at creation; per-claim approval-time check stays authoritative |
| Telegram length / abuse | Cap 10 links; per-user rate limits unchanged |
| Mixed M10 payout + M11 claim batch | Explicitly deferred; mixed messages clarify with zero artifacts |
| Nested idempotency collisions | Batch keys use the `…:claim:<n>` namespace, distinct from single-claim `…:claim` |
| Scope creep (CSV/pools/auto-approval/judge) | Explicitly deferred (§2); authority boundary tested (§10 items 42–49) |
